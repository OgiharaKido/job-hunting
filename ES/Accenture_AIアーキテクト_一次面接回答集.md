## ① 自己紹介（30秒）

**流れ**：大学・研究 → インターン2つ（データ基盤／エージェント＋受賞）→ AIで現場を変えたい

〇〇大学の荻原喜堂です。4年次から数理統計科学研究室で、医療・生体データの統計解析に取り組みます。学外では2つの長期インターンで、LLMを活用した企業情報の自動収集基盤と、製造業や大学向けの生成AIエージェントを開発し、後者ではNEDO主催のGENIAC-PRIZEで地域賞をいただきました。AIで産業の現場を変える仕事がしたく、AIアーキテクト職を志望しています。本日はよろしくお願いします。

## ② なぜアクセンチュアか（なぜコンサルもここで）

**流れ**：製造業×AIとフィジカルAI両方やる唯一の会社 → 原体験（又聞き開発vs直接対話）→ 業務に落ちて初めて価値 → Orchestrator・シェフラー → AIアーキという専門職種

一番の理由は、自分がやりたい「製造業の現場をAIで変えること」と、その先の「フィジカルAI」の両方に本気で取り組んでいる会社だからです。
自分自身インターンの経験の中で製造業の業務支援アプリを作成したことがあって、そのアプリでは職人の暗黙知的なところをAI、LLMを使って再現性のあるものにしようというアプリでした。そういったように製造業といったフィジカル的な部分ではまだまだLLMやAIを使って効率化できる部分が多くあると考えていて、製造業とAIを掛け合わせて日本の製造業のプレゼンスを上げていきたいと考えている。

### 深掘り「他の会社でもできるのでは？」

**流れ**：「作る」会社はある＝メーカー・自社に閉じる → 自分は「導入する」側 → SIerはこれから・コンサルは構想止まり → 実行してるのは貴社だけ

フィジカルAIまで視野に入れると他にないと考えています。「作る」会社はありますが、メーカーが自社の製品や工場のためにやるもので、一社に閉じます。私がやりたいのは様々な企業に「導入して」現場を変えることです。調べた限り、SIerは基盤を2026年度に公開予定という段階で、他のコンサルも構想支援が中心です。貴社はOrchestratorをすでに提供開始し、シェフラーと実機まで開発している。実行している唯一の会社だと考えています。

## ③ なぜAIアーキテクト職か（なぜDSじゃない）

**流れ**：面白いのは「毎日動くシステム」にするところ → 全レイヤー実装してきた → 価値はモデルよりデータの流れと運用の設計

モデルの精度より、AIを業務で毎日動き続けるシステムにするところに一番面白さを感じるからです。インターンでは、クローラー、RAGの推論部分、UI、AWS、ローカルLLM基盤まで全レイヤーを自分で設計・実装してきました。その中で、AIの価値はモデルよりもデータの流れと運用の設計で決まると実感しました。それを担うのがAIアーキテクトで、経験とやりたいことが一番重なる職種です。

## ④ 入社後やりたいこと

**流れ**：二段階 → ①製造業の暗黙知×生成AIエージェント（インダストリーXと協働、PoCで終わらせない）→ ②フィジカルAIで物理世界まで

二段階で考えています。まず、製造業の暗黙知の継承問題です。AIアーキテクトとして製造業案件に入り、加工判断のような熟練者頼みの業務に、図面や過去事例を統合した生成AIエージェントを組み込みたいです。インダストリーXのような現場を知る組織と協働できるのが貴社の強みだと理解しています。インターンではプロトタイプまでだったので、貴社ではPoCで終わらせず定着ま
でやりたいです。その先がフィジカルAIです。判断支援だけでなく物理世界でAIが動くところまで行けば、製造現場の人手不足を根本から解決できると考えています。

### 深掘り「なぜ製造業？」

**流れ**：労働代替の思い → 入口は導入が早い製造業 → 職人の暗黙知の衝撃 → 手応えもあった → 日本は製造業の国

根本は、労働力不足の日本で労働をAIで代替し、人が本当にやるべき仕事に集中できる世の中にしたいという思いです。その入口として導入が早いのが製造業です。インターンで、砥石選定がベテラン職人の感覚頼みで、その方がいないと回らない現場を見て、規模のある会社でもこうなのかと驚きました。同時に、図面や過去事例をAIで扱えば判断を支援できる手応えもありました。それに日本は製造業の国です。AIでプレゼンスをもっと上げたいです。

### 深掘り「なぜフィジカルAI？」

**流れ**：判断支援＝労働の一部だけ → 物理労働まで代替して初めて → Tesla FSD → 次は確実に物理世界

生成AIで代替できるのは労働の一部だけだからです。物理的な労働まで代替して初めて、人が本当にやるべき仕事に集中できると考えています。Tesla FSDのような実世界データで学習し続ける仕組みに注目していて、生成AIの次は確実に物理世界に来る。労働力不足を根本解決できるのはこの領域です。

### 深掘り「フィジカルAIの経験は？」

正直まだありません。ただ土台は、実世界からデータを集めてAIの判断を業務につなぐ基盤だと考えています。数千サイト規模の収集基盤や、図面という物理情報をAIで読んで判断につなげた経験は、そのまま効くと考えています。

### キャリアプラン

**流れ**：1-3年=実装力 → 中期=製造業知識で構想からリード → 長期=フィジカルAI領域

1〜3年はAIアーキテクトとして設計・実装力を磨き、システムを最後まで作り切れるようになりたいです。中期では製造業の業務知識を深めて構想段階からリードできるように、長期ではフィジカルAIの領域で製造業の変革を全体から描ける人材になりたいです。

## ⑤ ガクチカ（クローラー）＋技術ネタ

**流れ**：LLMクローラー改善 → 1000サイト・3割/60% → 手動設定の限界 → LLMで自動学習 → 8割/95%

最も力を入れたのは、LLMを活用したWebクローラーの改善です。約1000サイトから企業情報を収集する仕組みで、収集率3割・抽出精度60%に留まっていました。サイトごとに構造が違い手動設定が限界だったので、LLMでURLパターンやCSSセレクタを自動学習する機構を設計・実装し、収集率8割・精度95%まで改善しました。技術を業務課題に落とし込み、実用水準までやり切った経験です。

**深掘りへの返し**
- 役割は？ → タスクリーダーでした。社長の要望をシステム要件に分解してメンバーに割り振り、自分はLLM自動学習機構を担当しました。
- 苦労は？ → あるサイトの方法が別サイトで通用しないことです。個別対応をやめ、共通構造をLLMで抽出する方向に発想を切り替えました。
- 学びは？ → 優れた技術案より、現場で回る仕組みに落とし込める案の方が価値が大きいことです。

### 技術ネタ1：GENIAC受賞

**流れ**：研究相談×論文をつなぐエージェント → LLM対話ヒアリング→RAG検索→提案 → 一人で実装 → 地域賞250万 → 業務として成立する形まで作り込んだから

国立大学の研究室向けに、企業の研究相談と論文・技術シーズをつなぐAIエージェントを開発しました。スタッフが個別にヒアリングしていた業務を、LLMが対話で要件を聞き取り、RAGで論文を検索して手法を提案する形にし、対話管理から管理画面まで一人で実装、GENIAC-PRIZEで地域賞・懸賞金250万円をいただきました。受賞できたのは、ログを全部可視化して検証と改善が回る、業務として成立する形まで作り込んだからだと考えています。

### 技術ネタ2：製造業エージェント

**流れ**：砥石選定支援 → 図面→Vision解析→ルールで判定→RAG事例→LLM推奨 → 全部LLMに任せない → 一人で構築・デモ

精密金型メーカー向けの、研削加工の砥石選定・加工条件支援エージェントです。図面をアップすると、Vision APIで解析し、ルールベースで砥石を判定、RAGで類似事例を検索した上でLLMが推奨を出す構成です。こだわりは全部をLLMに任せないこと。確実な部分はルール、経験知は検索と生成に分けて、現場が信頼できる出力にしました。UIからDBまで一人で構築し、デモまで実施しました。

### 技術ネタ3：ローカルLLM基盤

**流れ**：API費増 → Mac百台規模×Ollamaで自前API → Ansible全自動・HAProxy負荷分散・Prometheus監視 → 定型はローカル・難問は外部の使い分け

外部APIのコストが増えていたので、社内のMac百台規模にOllamaを入れて自前のOpenAI互換APIサーバー群を作りました。Ansibleでサーバー化からモデル配布まで全自動化し、HAProxyでマシン性能に応じた負荷分散と本番・検証の分離、Prometheusで監視しています。記事選別のような大量・定型の推論をここに流し、難しい判断だけ外部APIに残す使い分け設計です。

**深掘りへの返し**
- なぜローカルで十分？ → 定型タスクにGPT-4級は過剰で、30Bクラスで精度十分と検証した上で移しました。
- なぜMac？ → Apple Siliconはユニファイドメモリで、30Bクラスが安価に動きます。社内資産の活用にもなりました。
- なぜminiで30B？ → MoE型で実際に動くのは3B分だけ、さらに4bit量子化で軽くしています。
- 工夫は？ → モデルは1台だけDLして残りは社内LANコピーで回線を保護、LB設定にはモデルを持つマシンだけ自動で組み込むようにしました。
- ⚠️ 台数・IPの詳細は言わない（「百台規模」まで）

### 技術ネタ4：AIツール

Claude Codeは設計の壁打ちとレビュー、Codexは最小変更の実装、と役割分担しています。出力は鵜呑みにせず、なぜその設計かを必ず確認し、基礎は本や一次情報で固めています。

## ⑥ チーム・対人系（核：対立＝優先順位の違い→先に認識をそろえる）

### チームで成し遂げた経験

**流れ**：タスクリーダー → 要件整理→適性で割り振り → 経験差→共有会 → 期限内完成 → 心がけ=最初に認識をそろえる

インターンで同期・先輩・オペレーターの方とデータ収集システムを開発しました。タスクリーダーとして社長の要件を整理し、得意分野でタスクを割り振りました。未経験メンバーもいたのでノウハウ共有の会を設け、詰まりを早めに拾い、期限内に完成させました。心がけたのは最初に目標と認識をそろえることです。

### 気の合わない人と仕事になったら

**流れ**：相手が大事にしているものを理解しに行く → 対立＝優先順位の違い → 野球の温度差を対話でまとめた → 共通目標を先に

まず相手が何を大事にしているかを理解しに行きます。対立の多くは性格ではなく優先順位の違いから生まれると感じています。高校野球でベンチ内外の温度差を、一人ひとり対話して共通の目標をそろえることでまとめた経験があります。先に共通目標を確認し、相手に合わせた伝え方をします。

### 意見が対立したら

**流れ**：前提を確認 → 社長のスピードvs自分の品質 → 成功の定義をそろえる → 言うべきことは率直に

まず相手の前提を確認します。結論の違いは評価軸の違いであることが多いからです。スピード重視の社長と品質重視の自分で分かれたときも、いつまでに何ができれば成功か、をそろえて落とし所を見つけました。その上で正しいと思うことは率直に伝えます。

## ⑦ 批判された経験・困難の決断（27卒実出題・最重要）

**流れ**：収集性能vs相手サイト負荷 → 並列＝速いが攻撃になりかねない → 1ページずつ＋自動停止を決断 → 効率を問う声→「継続運用できるか」を基準に説明

あります。クローラー開発で、収集性能と相手サイトへの負荷のトレードオフに直面しました。並列を増やせば速く成果も出ますが、相手サーバーへの攻撃になりかねません。私は1サイト1ページずつの順次リクエストと、エラーが続いたら自動停止する設計を決断しました。社内には効率を問う声もありましたが、継続的に運用できる仕組みかを判断基準として説明し、納得を得ました。

**予備**：野球（ベンチ外の自分が批判リスク承知でミーティングを開き、対話で統率）／社長直談判（品質のため時間確保を交渉）

## ⑧ 強み・弱み

### 強み

**流れ**：結果が出るまでやり切る → 野球の課題分析 → クローラー3割→8割

求められる結果が出るまで逃げずにやり切る力です。野球では試合に出るため課題を分析し修正を続け、インターンでも収集率3割・精度60%のクローラーを8割・95%まで改善しました。妥協せずやり切れるのが強みです。

### 弱み

**流れ**：早く形にしたくて実装に寄る → 設計が甘かった反省 → 今は書き出してから着手

早く形にしたい気持ちが強く、実装に寄りやすいところです。スピード重視で設計が甘かった反省があり、今は実装前に目的や責務を書き出してから着手し、周りに確認するようにしています。

（対人系なら）正論をストレートに言いすぎるところです。今は「自分はこう考えるけど、どう思うか」と一緒に考えるスタイルに変えています。
